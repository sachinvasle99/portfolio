01 — whoami

I build the platform,
and the AI that runs on it.

DevOps, SRE and platform engineering across cloud and bare metal — plus the GPU and inference layer that modern products now expect underneath them.

I have run that migration in both directions — on-premises onto EKS at one company, and EKS back onto our own hardware at the next. Very few people have done the second one.

Cloud to bare metal. At Krista AI, an enterprise AI automation company, we moved production off EKS and onto Kubernetes we run ourselves, and built the private cloud underneath it to do so — the compute, the networking, the storage and the platform services a managed control plane had been quietly providing. Cost and data residency drove the decision; delivering it meant owning every layer that AWS used to own for us.

Bare metal to cloud. Earlier, at Revent Labs, I ran it the other way: on-premises workloads onto EKS, with the whole footprint — VPCs, subnets, IAM, node groups and supporting services — as reusable Terraform and Terragrunt modules replicated across multiple regions for fast failover. Alongside it, ECR, Route 53, ELB, RDS and Aurora, Lambda and Secrets Manager, with least-privilege IAM throughout, plus GCP and GKE.

Running your own means no managed control plane to hide behind, so I own the whole lifecycle: control-plane and worker provisioning, etcd health and backups, rolling upgrades, certificate rotation, and the deep troubleshooting that lands on the API server, scheduler, kubelet, CoreDNS and the CNI. Node build-out is Ansible, so onboarding a machine is a playbook rather than an afternoon. On-call runs through PagerDuty, so a real failure reaches a phone rather than a channel nobody is reading.

Delivery is declarative all the way down. Jenkins runs from Jenkins Configuration as Code (JCasC) — controllers, plugins, credentials and jobs defined in YAML in Git, so a Jenkins instance is something you rebuild from a repository rather than a pet nobody dares restart, and a change to CI gets reviewed like any other change. Around it: GitHub Actions, GitLab CI and Bitbucket Pipelines running inside Kubernetes, JFrog Artifactory governing artifact promotion, and GitOps on ArgoCD and FluxCD giving teams self-service deploys with rollbacks that work.

Observability is one layer across the whole estate — Prometheus, Grafana, SigNoz, OpenTelemetry and ELK/EFK for metrics, logs and traces, with the dashboards and alerting that incident response actually runs on, and PagerDuty carrying the pages that matter.

On the AI side I run self-hosted LLM inference on on-premises GPU compute — model serving, GPU utilization, inference performance, context management and tool-calling — and I designed and wrote Krista XRay, the AI-powered SRE platform that uses it, where the model reasons over real production telemetry it is structurally forbidden from writing to. Next: Kubernetes orchestration for GPU workloads, and Go controllers with Kubebuilder.

01

Everything as code

Terraform and Terragrunt for infrastructure, Ansible for machines, Git as the source of truth for what is deployed. A change nobody can review is a change nobody can undo.

02

Read-only by default

Production starts at get, describe, logs. Anything that mutates a live cluster is named and confirmed — including for the tools I build.

03

Deterministic core, narrating edge

Code computes the evidence; the model interprets it. A number the LLM derived itself is a number nobody can reproduce.

04

Keep the model on our hardware

Self-hosted inference is not a cost exercise. It is what lets an investigation read production telemetry without shipping it to a third party.

04 — the thing I built

Software, not configuration.

Krista XRay

in production sole designer and developer

At 3 a.m., "the app is slow" used to mean opening four consoles and hoping somebody remembered what changed. Now it means asking one question and getting evidence back.

XRay is an AI-powered SRE platform that answers why is production slow or broken? It pulls from nine telemetry sources — Kubernetes, traces, logs, metrics, the data tier and the cloud APIs — correlates them on a shared timeline, works out what changed, ranks the probable causes, and explains the top ones in plain language with the evidence attached.

what it changes
  • The correlation nobody has time for. A human comparing a latency spike against deploy history, node pressure, slow queries and cache eviction is doing ten minutes of tab-switching under pressure. The platform does it on every investigation, the same way each time.
  • Change detection first. Most incidents are something that changed. Surfacing rollouts, config edits and scaling events in the same window as the symptom answers a large share of them outright.
  • Findings you can check. Every claim carries the query and the series it came from, so the reviewer can disagree with the tool instead of trusting it.
  • On-call that doesn't depend on who is awake. The knowledge lives in ranked hypotheses rather than in the one engineer who remembers this failure mode.
  • Nothing leaves the estate. Investigations can run entirely against self-hosted models on our own GPUs, which is what makes it usable where data residency rules out sending telemetry to a third party.
how it stays trustworthy

deterministic core

Python computes every number; the model only interprets. It cannot invent a latency figure because it never calculates one.

read-only by construction

All 16 tools are read-only and the service accounts are RBAC-scoped. There is no code path from a model output to a cluster write.

rank before you reason

A dependency graph scores probable causes first, so the model argues about a shortlist instead of trawling raw telemetry.

degrade loudly

A collector that can't reach its backend says so. Silently dropping a source lets you reason confidently from a hole in the evidence.

questions it answers
  • Why is checkout slow since 02:10?
  • What changed in the last hour?
  • Is this the app, the cluster, or the database?
  • Which service started this, and which are just downstream of it?
  • Has this failed this way before?
one investigation
  1. Symptom asked in plain language, not assembled from dashboards
  2. Collect nine sources queried in parallel, each degrading independently
  3. Correlate normalised onto one timeline; change detection over the same window
  4. Rank dependency graph scores candidate causes before any model sees them
  5. Explain agentic loop over 16 read-only tools, evidence cited per claim

Security in the pipeline,
not in a review meeting.

Guardrails belong on the delivery path itself. If a vulnerable image or a plaintext secret can only be caught by a person remembering to look, it will ship.

05a — compliance posture

Building for audited environments.

Enterprise customers arrive with a security questionnaire before they arrive with a workload. Designing for that up front is cheaper than retrofitting it.

SOC 2

Change management with a reviewable trail, least-privilege access, and logging and monitoring evidence that an auditor can actually be shown.

HIPAA

Encryption in transit and at rest, tightly scoped access to sensitive workloads, and tenant separation strong enough that neighbours cannot see each other.

Data residency

Dedicated single-tenant environments in the customer's own region, and self-hosted inference so telemetry and prompts never leave the estate.
