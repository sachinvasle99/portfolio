A WAF that 403s your PromQL

2026-09-09 · promql waf observability

While building cross-cluster investigations into our production environments, a subset of metric queries started coming back as 403 Forbidden. Not empty results, not a timeout, not a 401 — a flat rejection, and only for some queries.

The pattern took a while to see because it has nothing to do with what the query means. A query for a single series went through. The same query wrapped in an aggregation came back 403: 

rate(http_requests_total[5m])              → 200 OK
sum(rate(http_requests_total[5m]))        → 403 Forbidden
avg(node_memory_MemAvailable_bytes)       → 403 Forbidden
min(kube_pod_status_ready)                → 403 Forbidden
max(container_cpu_usage_seconds_total)    → 403 Forbidden
count(up)                                 → 403 Forbidden

Every failing expression contained one of sum(, avg(, min(, max( or count(. Those are, of course, exactly the aggregation functions you reach for the moment you stop looking at one pod and start looking at a cluster.

Why a WAF does this

Those five tokens are not interesting to Prometheus in the slightest. They are extremely interesting to a SQL-injection ruleset. A generic managed WAF rule group looks at the request — including the query string carrying the PromQL expression — sees an aggregate function immediately followed by an open parenthesis, and scores it as SQLi. The request never reaches the backend.

The failure is not in the query language, the query engine, or the credentials. It is a request-inspection layer applying database-shaped heuristics to a query language that happens to share five keywords with SQL.

This is the kind of thing that is invisible from either end. From the client it looks like an authorization problem, so you go and check tokens and RBAC. From the metrics backend it looks like the query was never sent, because it never was.

How to tell it apart from a real 403

  • Correlate on expression shape, not on scope or credentials. If sum(x) fails and x succeeds with the same token against the same endpoint, it is not authorization.
  • Look at the response body. An auth rejection from the metrics backend carries a backend-shaped error; a WAF block usually returns generic HTML or a support ID and none of your backend's error vocabulary.
  • Check where the 403 was logged. If the backend has no record of the request at all, something in front of it answered.
  • Try the same expression as a POST body rather than a query string — a difference in behaviour between the two points squarely at request inspection.

What this changed in how I build tooling

Any component that queries telemetry across an environment boundary is going through somebody's edge, and that edge has opinions. So per-collector degradation stopped being a nice-to-have: a collector that cannot get an answer has to report that it could not, name why, and let the rest of the investigation continue. An RCA tool that silently drops a data source is worse than one that says "no data from here" out loud, because the first one lets you reason confidently from a hole in the evidence.
